# Recipe Catalogue & Recipe Book

**Status: BUILT 2026-06-12.** Catalogue (**250 cards — the full recipe set**)
+ query API + autofill + recipe-book panel all delivered and merged.
`match_recipe` untouched. The book panel's *look/feel* is the Axolittle
playtest boundary (in-game, not headlessly screenshottable) — test sheet
`docs/test-sheets/2026-06-12-recipe-book.md`.

## TL;DR

Make recipes **enumerable** (for a recipe book, search, and "what can I
make?" hints) **without rewriting** the crafting matcher. Add a *data*
catalogue of `RecipeCard`s that **delegates** the actual craft to the
existing `crafting::match_recipe`. A consistency test proves every card
matches the live matcher, so the book can never advertise a craft the engine
won't honour.

## Why not a from-scratch registry rewrite

The investigation (2026-06-12, `crafting.rs`) found the matcher is **~180
effective recipes**, not the ~60 it looks like, because of three parametric
axes and several fuzzy/mirrored cases:

- **Parametric output** — tools (5 types × 5 materials via
  `material_from_slot`), bows (5 tiers via `bow_tier_from_slot`), armour
  (4 pieces × up-to-5 materials via `armour_material_from_slot`), and
  **5 dye-driven block families × 16 dyes** (`banner/sail/kite/
  paper_lantern/bunting_for_dye`) = ~80 outputs. Output depends on the
  material/dye in the slots, not a fixed item.
- **Fuzzy categories** — `is_logish_slot`, `is_any_planks`,
  `is_paperish_slot`: "any of a set", not a literal block.
- **Mixed order-sensitivity + mirroring** — 1×2/1×3 pairs are often
  order-insensitive (`is_pair`, `row_matches_set`); tools have mirrored
  left/right variants; some 1×3 rows are strictly directional (kite,
  lantern).

Two consequences:

1. A literal-pattern table **can't express** the parametric/fuzzy/mirrored
   recipes — the data model would need predicates and output-generators,
   i.e. it would re-encode the matcher's logic, not replace it.
2. A true characterization test (**prove new == old over all inputs**) is
   **impossible** — the grid space is 3⁹ × material/dye variants; it can't
   be brute-forced. So a rewrite's safety net would be a curated corpus, not
   a proof. Rewriting a working, well-tested core system on a partial net is
   poor risk/reward.

**The matcher is not the problem — its *non-enumerability* is.** So we add
enumerability beside it instead of replacing it.

## Design

### 1. The catalogue (data)

```rust
// crafting_catalogue.rs (new)

/// One browsable recipe. DESCRIBES a recipe for the book/search/hints; the
/// authority for what actually crafts stays `crafting::match_recipe`.
pub struct RecipeCard {
    /// What you get. For parametric families, one card per concrete output
    /// (e.g. an Iron Pickaxe card and a Diamond Pickaxe card).
    pub output: ItemStack,
    /// Shapeless bill of materials for display + search + "can I make this?".
    /// Fuzzy inputs carry a representative + a category tag.
    pub ingredients: Vec<RecipeIngredient>,
    /// A concrete grid that `match_recipe` maps to `output`. Drives
    /// click-to-craft (auto-fill) AND the consistency test.
    pub example_grid: [[CraftSlot; 3]; 3],
    pub category: RecipeCategory,
    /// Derived from example_grid bounds: does it need a workbench (3×3) or
    /// fits the 2×2 player grid?
    pub station: CraftStation,
}

pub struct RecipeIngredient {
    pub item: Item,           // representative item (for icon + count)
    pub count: u8,
    pub fuzzy: Option<FuzzyKind>, // Some(AnyLog) etc. → "Any log", matches a set
}

pub enum RecipeCategory { Tools, Combat, Building, Decoration, Food, Materials, Stations, Transport, Redstone }
pub enum CraftStation { PlayerGrid, Workbench }
pub enum FuzzyKind { AnyLog, AnyPlank, AnyPaper, ToolMaterial, ArmourMaterial, Dye }
```

### 2. Generation, not transcription

Parametric families are **generated by loops over the same tables the
matcher uses**, so they can't drift out of sync with the material/dye sets:

- Tools: `for mat in [Wood,Stone,Iron,Diamond,Satori] { for tool in [...] { card(grid_for(tool,mat), tool_of(mat)) } }`.
- Armour: per-piece material sets (Helmet/Boots allow Rubber; Chest/Legs don't — mirror the matcher's gate).
- Dye families: `for dye in ALL_DYES { card(banner_grid(dye), banner_for_dye(dye)) }`, ×5 families.

Literal recipes (planks, sticks, torches, stations, bells, …) are authored
explicitly. Total authored ≈ 70; generated ≈ 110.

### 3. Query API

```rust
pub fn all_cards() -> &'static [RecipeCard];
pub fn cards_in(category: RecipeCategory) -> impl Iterator<Item = &'static RecipeCard>;
pub fn search(query: &str) -> Vec<&'static RecipeCard>;           // name substring
/// Cards the player can afford right now (ingredient-aware, honours fuzzy sets).
pub fn craftable_now<'a>(inv: &Inventory) -> Vec<&'a RecipeCard>;
pub fn recipe_index_for_output(item: &Item) -> Option<usize>;     // forward: output → recipe
pub fn recipes_using(item: &Item) -> Vec<usize>;                  // reverse: ingredient → recipes (#46, JEI "uses")
```

Built once into a `LazyLock<Vec<RecipeCard>>`. The reverse "uses" map (#46,
2026-06-16) is a second `LazyLock<HashMap<(u8,u32), Vec<usize>>>` keyed by
`Item::sort_key`, built from the same cards' `ingredients` — so it's one derived
index, not a duplicate source of truth. Surfaced as **hover an item + U** in the
inventory (opens the book filtered to those recipes).

### 4. The consistency test (the safety net)

```rust
#[test]
fn every_card_matches_the_live_matcher() {
    for card in all_cards() {
        assert_eq!(
            crafting::match_recipe(&card.example_grid),
            Some(card.output.clone()),
            "card {:?} example grid does not produce its stated output", card.output
        );
    }
}
```

This is the whole risk story: a wrong/stale card fails CI; it can never
silently mis-craft, because the book only ever drives the real matcher.

> **Known gap (documented, not silently ignored):** the inverse — a matcher
> recipe with *no* card — can't be auto-detected (non-enumerability is the
> original problem). Mitigation: a `cards.len()` floor assertion + a
> maintenance checklist in the spec; severity is low (a missing card means a
> recipe isn't *browsable*, it still crafts manually). Closing this fully is
> the staged migration below.

### 5. Recipe book UI (to playtest boundary)

A panel reachable from the crafting screen. **Coexists** with the manual
grid (Minecraft-standard; preserves the 2026-06-12 slot-cursor work) — does
**not** replace it. Decisions taken (owner can override at playtest):

- **Layout:** left = category tabs + search; right = card grid (icon +
  name). Selecting a card shows its ingredient list.
- **Show-the-placement (revised 2026-06-12 per owner feedback):** selecting
  a card closes the book and **pins a placement-guide card** to the right of
  the result slot — a mini 3×3 showing exactly where each ingredient goes →
  the output. The player replicates the pattern themselves (learning the
  layout), or clicks **"⛏ Fill from bag"** to auto-lay it from inventory (the
  `autofill_from_example` path, now opt-in), or ✕ to dismiss. Affordability
  (green/grey) was "what you need"; the guide is "where it goes". No new
  crafting authority — Fill-from-bag still drives the real matcher.
- **Drill-down (2026-06-12):** each ingredient cell in the guide is
  interactive — hover shows its name; clicking a cell whose item is itself
  craftable jumps the guide to **that** recipe (shovel → click stick →
  sticks-from-planks). Raw inputs (cobblestone, iron ingot, wool) have no
  recipe and just show their name; craftable cells get a blue ring.
  Navigation is a stack (`pinned_recipe_stack`): a **"← Back"** button (and
  clicking the output icon) pops one level; ✕ clears. Lookup =
  `recipe_index_for_output(item)` (first card producing the item). Drill/back
  is mouse/touch; pad still pins from the book (per-cell pad nav of the guide
  deferred).
- **Text search (2026-06-13):** a 🔍 search box at the top of the book
  filters recipe names across **all** categories (case-insensitive substring,
  `visible_indices(category, search)`); auto-focused on open
  (`focus_book_search`), ✕ or switching tabs clears it. Keystrokes can't leak
  to gameplay because the focused egui `TextEdit` makes `main.rs`'s
  `egui_consumed` guard skip game input — the same mechanism the
  inventory-explorer search box relies on. `draw_recipe_book` takes
  `&mut CraftingUi` (split-borrowed against `&inventory` at the call site,
  mirroring the explorer). Search is keyboard/mouse/touch; a pad can't type,
  so LB/RB tab-switching clears search to reach the category lists.
- **Input parity:** pad (reuses the `PadSlot`/focus pattern from gamepad UI
  nav), mouse, touch — one egui surface, all three.
- **"Can I make it?":** `craftable_now` filters/sorts; afford = bright,
  unafford = dimmed.

### 6. Staged future migration (own spec, later — NOT now)

Once the catalogue exists and is trusted, *literal* recipes can migrate so
`match_recipe` consults the catalogue for them (shrinking the matcher to
just the genuinely-algorithmic fuzzy/parametric/mirrored cases). Incremental,
test-guarded by the same consistency test. This is how the "data-driven, not
match statements" CLAUDE.md rule gets fully satisfied — without a big-bang
rewrite. Explicitly deferred.
