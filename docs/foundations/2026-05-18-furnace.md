## TL;DR

Carve the **Furnace block** and the **generic Workstation framework** out of [Farming Tier 1.5](2026-05-14-farming-tier-1.5-processed-economy.md) Phases 2-3 and ship them as a standalone foundation. Doing so unblocks two specs that are otherwise waiting:

- **Spec 19 Blacksmith profession** — Spec 5 §3.13 says Blacksmith "registers its workstation hook but waits on Furnace shipping." A Furnace block ships the workstation hook and Blacksmith villagers come online immediately.
- **Spec 12 T1.5 itself** — when T1.5 builds, Phases 2-3 are already done.

This spec is **the engine's first block-entity primitive**. Spec 5 §3.7 designs the contract for container-style block entities; Spec 17 (Campfire) implemented the first concrete one but kept the state struct campfire-specific (it's literally in `world.block_entities: AHashMap<.., CampfireData>`). This spec generalises that map to `Box<dyn BlockEntity>` (or an enum, see Design choices) and lands the Furnace as the second concrete instance.

## Narrative

Today the engine cooks meat by putting raw beef in a vertical 2-slot crafting grid with coal underneath. That's the **Wave 6 furnace-in-grid hack** called out in `crafting.rs` as temporary. It's been temporary for a long time. Two things finally make the hack worth replacing:

1. **Spec 19 just shipped Cook villagers**, who claim a Campfire workstation. The Blacksmith profession has the same workstation-claim hook ready in `villager::Profession::from_workstation_block` (it's the only `_` branch with a `// future` comment); plugging a real Furnace block into that match completes Spec 19's profession surface.
2. **Spec 12 T1.5 needs the Workstation framework anyway** (Phase 2 of T1.5 is "block-entity framework"; Phase 3 is "Furnace as canonical workstation"). Shipping them as a prerequisite lets T1.5 focus on the crops + recipes work without paying for the engine plumbing twice.

## Scope (what's in)

- New `block::FURNACE` (and `FURNACE_LIT` if we go with two block-ids for the lit/unlit state — see Design choice 2).
- Generic block-entity framework: `WorldBlockEntities` upgraded from the campfire-only `AHashMap<(i32,i32,i32), CampfireData>` to a tagged enum or `Box<dyn BlockEntity>` mapping per cell. **The campfire stays a first-class entry** — this is a refactor, not a rip-out.
- `Furnace` block-entity state: input slot, fuel slot, output slot, recipe-in-progress tracker, tick-driven progress.
- Furnace UI: small egui panel similar to the crafting overlay, with three labelled slots + a progress arrow that fills as the smelt advances.
- Recipe table for furnaces: the existing smelting recipes from `crafting.rs::match_recipe` migrate here (raw meats → cooked meats; raw iron → iron ingot). The grid versions are flagged deprecated with a one-release migration window.
- Crafting recipe for FURNACE block: 8 cobblestone ringing an empty centre (Minecraft standard).
- Save/load via the same side-table pattern Spec 17 introduced.
- Spec 19 `Profession::from_workstation_block`: add the `block::FURNACE => Some(Profession::Blacksmith)` arm.
- Spec 5 §4.5 "Smelting" status flipped from "Wave 6 hack" to **DELIVERED**.

## Cross-economy hooks (added 2026-05-18 after meta-economy review)

Three explicit connections this spec should ship, per `docs/vision/sat-flow-and-economy-loops.md`:

### A. Cook quest pool requires Furnace use (Spec 19 integration)

Today Spec 19 Cook villagers offer `Make { item: Bread, count: 3 }` quests, but the completion check just inspects the player's inventory — it doesn't know whether the bread was baked at a Furnace or smuggled in from a chest. **Add a `requires_workstation: Option<BlockId>` field to `QuestFlavour::Make`**. Cook + Blacksmith Make quests set this to `Some(block::FURNACE)`. Completion check requires the player to have stood within 4 blocks of an active Furnace producing the target item in the last 30 seconds.

Without this, Furnace is decorative — a kid can complete Cook quests with bread bought from a Vendor Block. With it, the Furnace is a *workplace* and the Make-quest loop closes around the actual crafting station.

### B. Proof-of-Play hook on smelt-complete (optional)

The same HMAC-SHA256 primitive that runs on pickaxe strikes (`pop_server_secret`, Spec 6 §2.2) runs once per smelt-complete on Bitcoin-enabled servers when the smelting player has guardian-flag-enabled sats. Lower payout threshold than mining strikes (it's a passive trickle); same anti-X-ray architectural defence (server_secret never leaves the server). Off-Bitcoin servers and guardian-disabled players: smelting still works exactly the same, just no sats line.

Gives the kid a *set-and-forget* sats trickle while their furnace cooks dinner. Parallels Proof-of-Play's design philosophy: deterministic-payout-on-probabilistic-finding stays clean.

### C. Routes sats payouts through the unified helper

Any sats payout this Furnace ever does (PoP trickle in B above; any future repair-fee credit; etc.) goes through `apply_server_tax_and_payout` (see `docs/vision/sat-flow-and-economy-loops.md` §5). The helper is the single point of Reserve-drain + server-tax + Charter-flag gating. This Furnace foundation should write the helper if it's the first spec to need it.

## Scope (what's out — deferred)

- **Blast Furnace + Smoker variants.** Spec 5 §4.5 lists them; they're polish on top of the same workstation framework. Land them when there's gameplay demand.
- **Mill / Oven / Aging Rack.** Those are T1.5's job. This spec ships *only* the Furnace.
- **Hopper-driven item transfer between block entities.** Future polish — not in this scope and not in T1.5 either.
- **Smelting Blacksmith quest pool.** Falls out for free once the Profession arm goes live; the existing `BLACKSMITH_POOL` in `quest.rs` already has IronIngot + Coal Fetch quests that read sensibly against a working Furnace economy. No quest pool work in this spec.

## Design choices

### 1. Enum vs trait-object for block entities

`World.block_entities` is currently `AHashMap<(i32,i32,i32), CampfireData>`. Two reasonable upgrade paths:

- **Tagged enum**: `enum BlockEntityData { Campfire(CampfireData), Furnace(FurnaceData), ... }`. Pros: bincode-serialisable for free, no `dyn` overhead, easy save migration (one new variant). Cons: every new block-entity type touches the enum.
- **`Box<dyn BlockEntity>` trait object**: Pros: open-ended; new block entities can land without touching shared types. Cons: serialisation needs `typetag` or manual dispatch; small runtime overhead.

**Recommendation: enum.** AxeNStax's alpha block-entity count is small (Campfire today, +Furnace here, +Mill/Oven/Aging Rack in T1.5, +Chest later). The enum stays tractable. The trait object's openness is only worth it once we're building a plugin system, which is Spec 1 / Spec 8 territory, post-alpha.

### 2. One block-id or two for lit/unlit state

Campfire uses two block-ids (CAMPFIRE / CAMPFIRE_UNLIT) for visual state and bakes the fuel state into the block-entity. Furnace has the same lit-while-smelting visual flip.

**Recommendation: two block-ids** (FURNACE / FURNACE_LIT), matching Campfire's pattern. The renderer doesn't need to know about block-entity state to pick the right texture; it just reads the block-id. Lit-flip happens on smelt-start, un-lit on smelt-end.

### 3. UI: dedicated overlay or extend Crafting UI?

The Crafting UI is currently rendered via `craft_ui::draw_crafting_ui`. Furnace has a different shape (3 slots in a vertical column + progress arrow + output slot).

**Recommendation: new `furnace_ui::draw_furnace_ui` mirroring craft_ui.** The two paths share egui patterns (Background-order overlay, pinned-width Middle-order panel, layer_painter cursor item) — the Spec 5 §3.6 "Rendering pitfalls" subsection already documents both. Bundling them later (a generic "workstation UI" renderer) is post-T1.5 cleanup.

### 4. Progress display

Minecraft uses an animated arrow that fills left-to-right while smelting. egui's `ProgressBar` widget covers this cleanly. Bind it to `FurnaceData::smelt_progress / smelt_time` and re-render each frame the UI is open.

### 5. Auto-pulling vs manual-Take from the output slot

Pure quality-of-life. Minecraft requires the player to shift-click or drag the output. Modern modpacks often auto-eject to adjacent hoppers.

**Recommendation: manual Take only on alpha.** Hoppers are future-future. Auto-flow can land alongside the Hopper spec.

## Cross-game lift

- **Block-entity enum framework.** Engine-generic — any Decented voxel game reuses the framework as-is. Game-specific data drives which variants exist.
- **Workstation UI rendering pattern.** Egui-on-wgpu pattern is the same for any "input → output via timer" station in any game.
- **Fuel-ladder pattern.** Useful in any survival-flavoured Decented game.

Per shared infra strategy: the framework is engine-generic; the Furnace recipe table is AxeNStax-specific data. `furnace.rs` and `furnace_recipes.rs` keep that distinction visible at the file level.

## Bitcoin economy hook

Furnace itself doesn't touch the Bitcoin layer. Smelting is one of the "Bitcoin-spending" mechanics (trade-value goes up when raw items become processed items, per Spec 6 §13 which T1.5 introduces). This spec sits *under* that hook — it builds the workstation that T1.5 then teaches to add trade-value.

## Open design questions

1. **Furnace block-entity name on the wire.** Spec 5 §3.7 uses `genesis:furnace`. Sticking with that.
2. **Should mining a smelting Furnace lose the input + fuel + output?** Minecraft drops the input + output as items but loses the fuel. Mirror that — alpha-friendly. Configurable later.
3. **How does Blacksmith profession-claim handle a Furnace inside a house's interior?** Same as Carpenter + Crafting Table — the villager just needs to stand within 3 blocks at any point. Doors don't block claim scans. Fine.
4. **Does the smelt tick continue while no player is nearby?** Minecraft: yes. AxeNStax single-player: yes too — the campfire tick already runs every tick regardless of chunk-loaded state, so Furnace inherits that behaviour for parity.
5. **Recipe deprecation window length.** "One release" is hand-wavy. Pin it: 30 days after this spec lands, the grid-smelt arms get removed. Alpha is fast; longer windows don't reward anyone.

## Memory-rule check

- ✓ axenstax has farming — Furnace is the first proper food-processing workstation; the farming chain crosses into cooked output via this spec.
- ✓ economies vision — Furnace is the first step on the processed-trade-value ladder. Vendor Block (separate spec, same date) consumes the increased trade-value.
- ✓ bitcoin parent controlled — no fresh compliance surface; trade-value sats are gated by T1.5's §13 work, not by this spec.
- ✓ shared infra strategy — block-entity framework is engine-generic; data tables are game-specific.
- ✓ uk english naming — "Smelt" not "smeltz"; "Furnace" is British-standard.
- ✓ proof of play is proof of work — orthogonal. Smelting is not a hashing mechanic.
