# Tip Jar Block — first spectator-economy primitive

**Status:** Phases 2-13 DELIVERED 2026-05-23 on `feat/tip-jar`. Phase N = Axolittle playtest gate (open).
**Branch:** `feat/tip-jar` off `main`.
**Trigger:** Goal-driven solo dev cycle, Round 2. Picked from `docs/vision/economies-long-run.md` §10.1 — "Tip Jar (T2)" — as the smallest, most self-contained, highest-leverage spectator-economy opener. The vision describes it as "Tiny primitive — lifts cross-game" (queue entry B7).

---

## TL;DR

A new placeable block — `TIP_JAR` (id 125) — that any player can right-click to send sats to its owner. The owner is captured at place-time (`TipJarOwner::LocalPlayer(pidx)` for v1, BRIDGE to `Npub(String)` when the Signet pubkey wiring lands; see *Known limitations*). Right-click opens a small dialog with preset amounts (1 / 5 / 25 / 100 sats) + an "Other" custom-amount field; clicking a preset fires `economy::apply_sats_payout(amount, PayoutKind::Tip, _, _)`. On Charter-off / Bitcoin-disabled, the dialog shows "Tipping requires Bitcoin enabled for this account" and is read-only.

The owner accrues sats via `TipJarData.escrow_sats`. The owner right-clicks their own jar to see a *Withdraw* button instead (mirrors the Vendor Block `OwnerWithdrawEscrow` pattern).

1 new BlockId (125), 1 new MaterialId (`TipJarItem`), 1 new `PayoutKind::Tip`, 1 new block-entity variant (`BlockEntityData::TipJar(TipJarData)`), 1 new module (`tip_jar.rs`), 1 new UI module (`tip_jar_ui.rs`), 1 new recipe (1 IronIngot + 8 planks ring — same shape as Vendor Block, **discriminated by output**: planks here vs IronIngot centre is shared with Vendor, so we use **GoldNugget** at centre instead to keep recipes orthogonal — see Recipe section). **Estimated ~750 LOC including tests.** PROTOCOL_VERSION 31 → 32.

Independent of every other open spec. Touches only files Round 1's bounty work also touched (`block.rs`, `item.rs`, `crafting.rs`, `economy.rs`, `save.rs`, `world.rs`, `player_slot.rs`, `game_loop.rs`, `server.rs`, `protocol.rs`, `texture_gen.rs`) — pattern is well-established by now.

---

## Why this lives here

- **First spectator-economy primitive.** Until now, every sats-paying loop is a producer / consumer / combatant relationship (mining, quests, vendors, bounties, raids, plaque tips). A Tip Jar is **valueless effort recognised at distance** — a streamer being tipped, a builder being thanked for a public road, a Nostrich tamer being thanked for the show. The mechanic teaches "things in the world can be appreciated".
- **Cross-game lifts.** Every Decented game with watchable players (any of them) can ship the same TIP_JAR block. The block + payout-kind + audit hash are AxeNStax-agnostic.
- **Foundation for Tournament Broadcasts (10.2) + Highlight Clips (10.3).** Both extend the same "tip flow with a content backdrop" primitive.
- **Closes the architect-tip pattern hole.** Spec 25 Phase 7 added Plaque tipping but that's tied to a specific *building*. Tip Jar is the generic version — tip a *player*, not a *thing*.

| ID | Block | Mining behaviour | Notes |
|---|---|---|---|
| 125 | `TIP_JAR` | Drops itself (`TipJarItem` material) **if the player breaking it is the owner**; non-owners get an anti-grief refusal toast (mirrors `vendor::cleanup_vendor`). | Decorative jar shape baked into the block face. |

**Recipe (3×3):**
```
P P P
P G P
P P P
```
8 planks (species-neutral via `is_any_planks`) + 1 **GoldNugget** at centre → 1 TIP_JAR. GoldNugget rather than IronIngot avoids the recipe collision with Vendor Block (which uses iron at centre + OAK_PLANKS specifically). Thematically apt — a gold-plated tip jar reads "value here". If GoldNugget doesn't exist yet (likely), fall back to **2 IronIngot** stacked vertically at centre — checked separately from the iron+planks-ring Vendor recipe via a centre-stack predicate.

### 2. New `tip_jar.rs` module

Pure helpers + the block-entity type. Mirrors the `vendor.rs` shape:

```rust
/// Owner of a tip jar. Two variants:
/// - LocalPlayer(pidx) — alpha. Pidx-stable across save+reload as long
///   as the player count is preserved.
/// - Npub(String) — the post-Spec-1-Phase-4 stable owner shape. Survives
///   any save+reload + transcends the LocalPlayer split-screen edge case
///   (a world saved with Player 2 owning a jar then reloaded solo would
///   lock Player 0 out of withdrawing under the LocalPlayer variant).
#[derive(Clone, Debug, Serialize, Deserialize, PartialEq)]
pub enum TipJarOwner {
    LocalPlayer(usize),
    Npub(String),
}

/// Per-jar state. Lives in `World.block_entities` via `BlockEntityData::TipJar`.
#[derive(Clone, Debug, Default, Serialize, Deserialize, PartialEq)]
pub struct TipJarData {
    pub owner: Option<TipJarOwner>,
    pub escrow_sats: u64,
    /// Tick count of the last tip received — drives a brief sparkle
    /// animation on the block (BRIDGE — animation hook not yet wired).
    pub last_tip_tick: u64,
    /// Total tips ever received (informational; surfaces in the owner's
    /// withdraw dialog as "lifetime tips").
    pub lifetime_tips_received: u64,
}

/// Pure try_tip helper — defensive checks + escrow accrual.
pub fn try_tip(
    data: &mut TipJarData,
    tipper_pidx: usize,
    amount_sats: u64,
    current_tick: u64,
) -> TipOutcome { /* ... */ }

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum TipOutcome {
    Accepted { credited_to_escrow: u64 },
    /// Player tried to tip their own jar — defensive (UI hides the
    /// tip buttons for owners). Returns silently.
    SelfTipBlocked,
    /// Amount was 0 — UI shouldn't fire this; defensive.
    ZeroAmount,
    /// Owner not set (the jar was placed but somehow has no owner —
    /// shouldn't happen since place-time stamps it).
    NoOwner,
}

/// Pure try_withdraw — drains escrow into the caller-returned amount.
pub fn try_withdraw(data: &mut TipJarData, requesting_pidx: usize) -> u64;

/// HMAC audit hash for a tip event — mirrors `bounty::claim_audit_hash`.
/// Tipper + recipient + amount + server_secret → 32 bytes.
pub fn tip_audit_hash(
    tipper_pubkey: &[u8; 32],
    recipient_pubkey: &[u8; 32],
    amount_sats: u64,
    server_secret: &[u8],
) -> [u8; 32];
```

### 5. `tip_jar_ui.rs` — tip dialog

Two views, chosen by `is_owner`:

**Non-owner (tipper) view:**
- Header: *"Tip Jar — {owner_label}"* (owner_label = "Player 1" for LocalPlayer(0) etc.; post-Phase-4 it's the npub).
- Preset buttons: **1 sat**, **5 sats**, **25 sats**, **100 sats** — each enabled only when the player's sats_balance ≥ that amount AND Charter+Bitcoin allow.
- Custom-amount input field (post-MVP if budget allows; defer to v2 otherwise).
- Charter-off / Bitcoin-disabled: dialog shows *"Tipping requires Bitcoin enabled for this account."* — all buttons disabled.

**Owner view:**
- Header: *"Your Tip Jar"*.
- Counters: *"In jar: N sats"* + *"Lifetime received: M sats"*.
- **Withdraw** button — moves `escrow_sats → player.sats_balance`.

Esc / 'E' closes (matches the Spec 29 Furnace UX convention + Bounty Board precedent).

### 6. Right-click + place wiring in `game_loop.rs`

- **Place-time:** when a player places a TIP_JAR, `world.block_entities` gets a new `TipJar(TipJarData { owner: Some(LocalPlayer(pidx)), .. })` entry.
- **Right-click TIP_JAR:** set `player.open_tip_jar = Some((x, y, z))` — opens the dialog.
- **Anti-grief on break:** non-owners hitting an owned TIP_JAR get the same refusal pattern as Vendor Block (`vendor.rs::cleanup_vendor`).
- **Per-frame dialog branch:** alongside the existing vendor/furnace/chest/bounty dialog ladder.

### 7. Claim path — fire payout + Vow check + audit

Mirrors the Bounty Board claim handler exactly:
1. `tip_jar::try_tip(&mut data, tipper_pidx, amount, tick_counter)` — drains the tipper's sats balance, accrues to escrow.
2. **Nostrich Vow check:** the tipper's `nostrich_vow::is_vow_active()` blocks the tip (vow suppresses ALL sats outflows).
3. **apply_sats_payout** — routed for the tipper's "amount sent" log line + server skim accounting + Reserve drain. The actual credit is to `escrow_sats` not to a player directly (the owner withdraws separately), so the payout result's `credited` flows back into `data.escrow_sats`.
4. **Audit hash** to log:
   ```rust
   let tipper_pubkey = [0u8; 32]; // BRIDGE: pubkey-from-signet — replace when Spec 1 Phase 4 signing bridge lands.
   let recipient_pubkey = [0u8; 32]; // BRIDGE: same — TipJarOwner::Npub variant feeds this once live.
   let h = tip_jar::tip_audit_hash(&tipper_pubkey, &recipient_pubkey, amount, &server_secret);
   log::info!("tip {amount} sats by p{tipper_pidx} → owner {:?} hash={:02x}{:02x}{:02x}{:02x}", data.owner, h[0], h[1], h[2], h[3]);
   ```

## Known limitations (documented BRIDGEs)

1. **`LocalPlayer(pidx)` ownership has a single-player-reload edge case** (pre-existing on Vendor Block per Round 2 pre-build audit). A world saved with Player 2 owning a TIP_JAR then reloaded solo locks Player 0 out of withdrawing. **BRIDGE:** `// BRIDGE: TipJarOwner::LocalPlayer(pidx) breaks under split-screen → solo reload. Replace with TipJarOwner::Npub(String) when the Signet pubkey is plumbed in via Spec 1 Phase 4 — this fix should also cover VendorOwner::LocalPlayer.` In `tip_jar.rs`.
2. **Audit hash uses zeroed pubkey placeholders** (same pattern as the bounty claim handler). **BRIDGE:** `// BRIDGE: pubkey-from-signet — replace when Spec 1 Phase 4 signing bridge lands.` Comment also notes the trigger explicitly (per Round 2 audit feedback — the Bounty Board's equivalent comment is missing the trigger; back-fill in this PR while we're there).
3. **Audit log is informational only.** Server-side replay verification of tip flows waits on Spec 1 Phase 4 + the Lightning settlement layer (currently itself a BRIDGE in `apply_sats_payout`).

## Cross-spec interactions

- **Vendor Block** — same owner-pidx pattern; both have the latent single-player-reload edge. Tip Jar's BRIDGE note explicitly calls for the Npub migration to cover both blocks together.
- **Spec 25 Plaque tipping** — Plaque tips are tied to a specific building's plaque chain (per-architect). Tip Jar is generic per-player. The two coexist cleanly; no shared code.
- **Nostrich Vow** — vow suppresses ALL sats outflows for the cursed player. Tipping check honours this exactly as the bounty claim path does.
- **Server economy policy** — both `bitcoin_enabled` + Charter-flag gates are honoured. On Bitcoin-disabled servers, the dialog is read-only; no rep fallback (tipping has no meaningful rep equivalent — tip is voluntary value transfer, rep is village-bound).
