# Spec Drift Audit — 2026-04-18

**Status**: Addendum to specs 01, 02, 04, 05. The main spec bodies haven't
been re-edited yet; this doc is the canonical statement of what changed after
the server-authority extraction (see
`docs/superpowers/specs/2026-04-18-server-authority-extraction.md`).
Spec bodies get folded back in on a later pass.

**Triggered by**: Tasks 1a–1d of the server-authority extraction. Code changes:
protocol V2, `GameServer::tick` phase order, `PlayerIntent::from_input_packet`,
`ServerPlayer.server_simulated`, speed-cap anti-cheat seed, mob spawning /
falling blocks as pure free functions.

---

## Spec 01 — Engine Architecture

### Matches
- 20 TPS tick, 50 ms per tick (`server.rs:277`).
- World-time advances `+4` per tick, 24000-tick day cycle (`server.rs:279`).
- hecs ECS (`server.rs:96`).

### Drift
- **§4.1 tick order.** Spec lists `Network Recv → Input Processing → World
  Simulation (Physics → Block updates → Entity AI → Scheduled ticks → Plugins)
  → World Gen Check → State Snapshot → Network Send → Persistence → Metrics`.
  Actual `GameServer::tick` (`server.rs:277-350`) executes: `world_time →
  mob_spawning → falling_blocks → water/leaf decay → player_physics → mob_ai
  → entity_physics → combat → despawn`. Divergence is deliberate — spec phase
  order is the target; Task 1d only moved player physics onto the server. The
  spec should be reworded to describe the current order as a milestone, with
  the full spec order as the endpoint once State Snapshot and explicit
  Network Recv phases land.
- **§4.1 input processing.** Spec places input as step 2 of the tick. Actual
  input processing happens outside the tick — `hosted_server.rs:345-389` does
  the per-packet parse/validate + sets `sp.pending_intent`, then `server.tick`
  consumes it. Document this pre-tick boundary.

### Gaps
- Server-driven physics for remote players is missing from the spec entirely.
  Add §4.1 subsection: `PlayerIntent::from_input_packet` → `Player::tick` on
  server, keyed off `ServerPlayer.server_simulated`.
- Speed-cap anti-cheat (`server.rs:362-393`, 1.5 × sprint speed horizontal
  clamp per tick). Document as a spec 08 cross-reference.

## Spec 02 — World Format

### Matches
- Block IDs are u16; GRAVITY flag defined in `BlockFlags` (`block.rs`).
- Chunk format 16×16×16.

### Drift
- **Falling blocks extraction**. Spec treats block updates as part of the
  generic tick-loop block update phase. Actual: `falling_blocks.rs` is a pure
  free function returning `Vec<BlockChange>`, gated to run every 4th tick
  (5 Hz) and scanning 16 blocks around each player (`falling_blocks.rs:20-48`).
  Spec should pin the 5 Hz cadence, the per-player scan radius, and the water
  displacement behaviour when sand lands on water.

### Gaps
- `BlockChange { x, y, z, new_block }` struct lives in `protocol.rs:127-133`.
  Spec 02 or 04 should cross-reference it.

## Spec 04 — Networking

### Matches
- Packet-type enumeration, reliability class per packet type, unreliable Input
  datagram every tick.

### Drift
- **Protocol version**. Spec still describes V1. `protocol.rs:251` is now
  `PROTOCOL_VERSION = 2`. Changelog block at `protocol.rs:243-250` is the
  authoritative record: *"v2 (2026-04-18): StateUpdatePacket gains entity
  spawns/updates/despawns and last_acked_input for prediction reconciliation."*
  Spec needs a §10 subsection for V2.
- **StateUpdatePacket wire shape.** Spec lists packet types but not field
  shapes. Code has `tick, players, block_changes, world_time, last_acked_input,
  entity_spawns, entity_updates, entity_despawns` (`protocol.rs:172-193`).
- **InputPacket wire shape.** Same — field-by-field documentation missing from
  the spec; `protocol.rs:81-109` is canonical.

### Gaps
- `EntitySpawn`, `EntityUpdate`, `EntityKind` — all new structs
  (`protocol.rs:138-170`). Add to §2.3.
- `last_acked_input: u64` — the keystone field for the client-side
  predict-and-replay loop described in the server-authority design spec §4.
  Must appear in spec 04's state-sync section.

## Spec 05 — Gameplay Systems

### Matches
- Sprint speed 21.78 b/s (`server.rs:363`). Walk/sprint/sneak constants match
  spec §1.1 (`physics.rs:13-17`).
- Mob spawn cycle every 400 ticks = 20 s (`server.rs:287`, spec §9.4).
- Mob soft cap 80 (`spawning.rs:64`).

### Drift
- **§12.1 `PlayerIntent` struct**. Spec shows boolean `move_forward/backward/
  left/right`. Code (`player_intent.rs:11-65`) uses analog `move_forward: f32`
  and `move_right: f32` (–1.0..=1.0), plus split `jump_held`/`jump_pressed`
  events, plus `scroll_delta`, `toggle_debug`, `cursor_captured`. The analog
  form is strictly more expressive (gamepad sticks) and should be the spec.
- **Mob spawning form**. Now a pure free function `spawning::tick_mob_spawning`
  — no ECS ownership, no `self`. Call sites in `server.rs:286` and
  `game_loop.rs:79`. Spec should describe as a pure function, not a method.

### Gaps
- `PlayerIntent::from_input_packet` helper. Document where wire-intent
  becomes engine-intent on the server side.
- Server-side remote-player physics path, speed cap, `server_simulated`
  flag. Spec 05 §1 (movement) needs a subsection on server-authoritative
  simulation for remote clients.
